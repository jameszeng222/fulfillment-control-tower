> 文档版本：V1.1
> 产品定位：物流轨迹监控、预警与渠道时效分析
> 主要用户：物流部、客服部、系统管理员
> 优先级范围：P0 可开发版本
> 初版日期：2026-08-13
> 更新日期：2026-08-24

---

## 1. 文档目的

本文档用于指导产品、设计、前端、后端、数据和测试团队完成物流轨迹预警监控系统的设计、开发和验收。

系统不是订单全链路 ERP，也不是客服工单系统。系统以履约单和运单为监控对象，以 ERP 履约数据和 17TRACK 轨迹数据为事实来源，解决以下问题：

1. 主动发现未上网、断更、停滞、卡关、运输超时、派送失败和退运等物流问题。
2. 保留 17TRACK 原始主状态和子状态，同时叠加公司自己的业务预警，避免状态互相覆盖。
3. 为物流部提供渠道、国家和仓库维度的时效与稳定性分析。
4. 为客服提供需要联系客户的包裹、已处理标签和服务单跳转入口。
5. 将同步失败、字段缺失等数据质量问题与真实物流异常分开管理。

## 2. 产品定位与设计原则

### 2.1 产品定位

一句话定义：基于 17TRACK 物流事实，自动识别需要物流部或客服关注的运单，并分析不同渠道的时效与稳定性。

### 2.2 设计原则

1. **事实不改写**：17TRACK 主状态、子状态和原始轨迹必须原样保存和展示。
2. **预警是判断，不是状态**：运输超时、断更等属于业务规则输出，不替换 17TRACK 状态。
3. **数据异常不等于物流异常**：17TRACK 同步失败时暂停时间类判断，不允许误报未上网或断更。
4. **一单多预警但只计一次当前异常包裹**：保留主预警和次预警，避免列表重复和总量重复。
5. **恢复自动退出，历史可追溯**：恢复正常后退出当前异常列表，但保留命中、处理和恢复记录。
6. **物流监控为主，客服协作为辅**：不建设独立工单、AI、通知中心、索赔和重型模板模块。
7. **规则配置化**：渠道时效、工作日历、国家差异、阈值和排除条件不得硬编码在前端。

### 2.3 V1.1 关键更新

1. 监控页面由“七类平铺预警”收口为 **6 个一级业务分类 + 10 条底层规则**，列表更轻，规则仍可独立配置。
2. 增加 ERP 前置监控：履约单报错、履约单生成后 24 小时未签出。
3. 团队范围确定为 LM、FD、LM_TT、网红团队，并支持全部团队快速切换。
4. 发货仓筛选只保留万邑通仓、国内仓；增加与发货仓联动的 C 端物流渠道筛选。
5. 明确异常路由：延误归入运输异常；清关补资料归入卡关；收件人拒收归入派送异常；其他异常只作为兜底。
6. 手动归档仅归档业务预警，17TRACK 主状态、子状态和历史轨迹永久保留；已签收自动归档。

## 3. 目标与成功指标

### 3.1 产品目标

1. 物流异常从“客户反馈后发现”转为“系统主动发现”。
2. 物流部可在一个页面定位异常运单、查看完整轨迹并判断影响范围。
3. 客服无需跨系统查找即可识别需要联客的包裹和关联服务单。
4. 管理者能够比较渠道在不同国家的时效、稳定性和末端派送质量。

### 3.2 上线后建议指标

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 轨迹数据可用率 | 同步成功且关键字段完整的监控运单 / 监控运单 | ≥ 98% |
| 预警计算延迟 | 新轨迹入库至预警结果更新的时间 | P95 ≤ 10 分钟 |
| 误报率 | 经人工确认不符合规则的预警 / 已确认预警 | ≤ 5% |
| 恢复更新延迟 | 恢复轨迹入库至退出当前异常列表的时间 | P95 ≤ 10 分钟 |
| 预警处理覆盖率 | 已处理预警 / 应处理预警 | 上线后按团队设定 |

## 4. 范围定义

### 4.1 P0 本期开发范围

1. 数据总览。
2. 轨迹监控与运单追踪合并页面。
3. 六个一级业务预警分类和十条底层规则。
4. 17TRACK 九类主状态及子状态展示。
5. 物流轨迹详情与预警判断依据。
6. 预警生命周期、处理标签、备注和归档。
7. 渠道时效、稳定性和末端派送质量分析。
8. 渠道 × 国家 SLA 规则配置。
9. ERP/Excel 履约单导入和数据校验。
10. 17TRACK 同步状态与数据健康监控。
11. 物流部、客服、管理员三个角色的权限和默认视图。
12. LM、FD、LM_TT、网红团队切换，以及万邑通仓/国内仓和 C 端物流渠道联动筛选。

### 4.2 P1 可后续增加

1. 日报或即时通讯机器人摘要推送，不建设站内通知中心。
2. UCC 服务单状态回传和详情跳转。
3. TOS 重发、退款结果回传，用于自动生成“二次异常”业务标签。
4. 客服轻量联客入口或调用现有联客系统。
5. 客诉率、丢件率等关联指标。

### 4.3 本期明确不做

1. 支付、库存、加工、仓储等完整订单全链路监控。
2. 独立工单中心。
3. AI 邮件或群消息识别。
4. 独立通知中心。
5. 索赔管理、赔付审批和财务结算。
6. 新建客服模板库和消息发送平台。
7. 物流隐性成本核算。
8. 替代 UCC、TOS、ERP 或 17TRACK 的原系统能力。

## 6. 核心概念与状态模型

### 6.1 追踪唯一键

`tracking_key = normalized_tracking_number + carrier_code`

说明：

1. 运单号必须按文本保存，保留前导零和全部精度。
2. `carrier_code` 使用 17TRACK 运输商代码。
3. 同一运单号在不同运输商下不得直接去重。
4. 一个履约单允许关联多个运单；一个订单允许关联多个履约单。

### 6.2 三层状态模型

#### A. 物流事实层

存储 17TRACK 返回的原始状态：

| 主状态 | 中文展示 |
|---|---|
| NotFound | 查询不到 |
| InfoReceived | 已收到信息 |
| InTransit | 运输途中 |
| Expired | 运输过久 |
| AvailableForPickup | 等待自提 |
| OutForDelivery | 派送途中 |
| DeliveryFailure | 派送失败 |
| Delivered | 已签收 |
| Exception | 物流异常 |

子状态使用 17TRACK 返回值原样保存，例如 `DeliveryFailure_InvalidAddress`、`Exception_Returning`。前端同时展示代码和中文描述。

#### B. 业务判断层

系统根据 ERP、17TRACK、SLA 和日历计算业务预警。前台只展示 6 个一级分类，后台保留 10 条底层规则：

| 一级业务分类 | 底层规则 | 主要处理人 |
|---|---|---|
| 履约准备异常 | 履约单报错、超时未签出 | 物流部/业务/仓库 |
| 未上网异常 | 物流未上网 | 物流部 |
| 运输异常 | 运输超时、物流断更、物流停滞、海关卡关 | 物流部 |
| 派送异常 | 派送失败/等待自提/拒收等末端异常 | 客服部为主，物流部协同 |
| 包裹退运 | 包裹退运 | 物流部/客服部 |
| 其他异常 | 未命中明确规则的17TRACK异常兜底 | 物流部 |

一级分类用于页面导航和统计，底层规则用于独立配置、命中证据、恢复判断和明细筛选。17TRACK状态不计入上述业务分类，也不会被业务分类改写。

#### C. 数据健康层

| 状态 | 定义 |
|---|---|
| success | 最近一次同步成功，允许参与规则计算 |
| failure | 最近一次同步失败，暂停依赖轨迹的时间类判断 |
| stopped | 运单不再同步，例如达到接口期限或被管理员停止 |

### 6.3 监控生命周期

| 状态 | 定义 | 列表行为 |
|---|---|---|
| active | 当前至少有一个有效预警 | 出现在“当前预警” |
| recovered | 曾命中预警，当前已恢复 | 退出当前预警，可在历史中查询 |
| normal | 从未命中或当前无业务预警 | 仅在“全部运单”展示 |
| archived | 业务监控被手动归档或已签收自动归档 | 退出当前预警；17TRACK状态和轨迹仍可在全部运单/详情查询 |

### 6.4 业务标签

业务标签与物流状态、预警类型分开保存。P0 支持：

- 待跟进
- 已跟进
- 已解决
- 已联系客户
- 已重发
- 已退款
- 二次异常
- 手动归档

“二次异常”仅作为业务标签：物流断更或未上网订单已重发/退款后，原包裹恢复运输或最终妥投时自动标记。它不属于当前实时物流预警。

### 6.5 监控组织范围

| 维度 | P0取值 | 说明 |
|---|---|---|
| 团队 | LM、FD、LM_TT、网红团队 | 页面支持全部团队和单团队切换；所有统计与列表同口径联动 |
| 发货仓 | 万邑通仓、国内仓 | 页面只保留两个业务仓库分组；底层可映射多个ERP仓库代码 |
| 物流渠道 | 公司内部渠道字典 | 用于采购、SLA和渠道质量分析 |
| C端物流商 | 按发货仓和渠道映射 | 用于消费者实际末端承运表现和列表筛选 |

仓库代码与业务仓库分组通过配置表维护，不在页面硬编码。导入未知仓库代码时进入数据质量列表，不得静默归入国内仓。

## 7. 预警规则

### 7.1 通用计算约束

1. 时间统一以 UTC 存储，页面按用户时区展示；默认业务时区为 Asia/Shanghai。
2. “工作日”根据目的国家工作日历计算，支持节假日配置。
3. “自然日”按连续 24 小时计算，不排除周末和节假日。
4. 轨迹事件必须先完成时间、地点、状态和有效性标准化，再参与计算。
5. 同一运单可命中多个预警；系统保存全部命中结果，并选择一个主预警用于列表归类。
6. 当前异常包裹总量按 `tracking_key` 去重；各预警类型数量允许分别统计命中次数。
7. 同一规则在未恢复前不得重复创建新的预警实例，只更新持续时间和最新证据。

### 7.2 主预警优先级

默认优先级从高到低：履约单报错 > 包裹退运 > 派送异常 > 海关卡关 > 超时未签出 > 物流未上网 > 物流断更 > 物流停滞 > 运输超时。其他异常只在没有命中明确分类时兜底，不参与覆盖明确分类。

管理员可配置优先级，但不能删除原始命中记录。

### 7.3 R01 履约单报错

**命中条件**：ERP 建单、履约单生成或物流取号任务返回失败，导致履约单或物流单号无法正常生成。错误原因包括但不限于城市、详细地址、邮编校验失败、物流产品不可用和取号失败。

**数据来源**：ERP 错误中心。此时可能尚无履约单号或运单号，使用订单号和 ERP 任务号作为临时跟踪键。

**恢复条件**：ERP 修复数据并重试成功，生成履约单和运单号。成功后自动关联正式履约单，并进入17TRACK轨迹监控。

**展示证据**：订单号、ERP任务号、错误码、错误摘要、创建时间、已等待时长、发货仓、所属团队。

### 7.4 R02 超时未签出

**命中条件**：履约单已经生成，但从履约单创建时间起超过 24 小时仍没有 ERP 签出时间。

**排除条件**：订单已取消、履约单已冻结、测试数据或缺少履约单创建时间。

**恢复条件**：ERP 回传签出时间。签出后结束该预警，并在生成运单号后进入未上网和轨迹类规则。

**展示证据**：履约单号、订单号、履约单创建时间、当前ERP阶段、发货仓、等待时长。

### 7.5 R03 物流未上网

**命中条件**：ERP 显示已签出/已发货后超过 2 个自然日，仍未产生承运商有效首扫。

以下事件不算有效首扫：InfoReceived、电子面单创建、预报数据、Shipping Label Created 等仅表明承运商收到信息的事件。

**排除条件**：同步失败、缺少签出时间、运单号或运输商代码无效、已经产生有效首扫。

**恢复条件**：产生 PickedUp、Acceptance、InTransit 等有效承运商实体扫描。恢复后从当前预警退出，不保留独立历史列表，只在履约单详情的预警历史中保留触发时间、恢复时间、持续时长和恢复证据。

**展示证据**：ERP 签出时间、首条 17TRACK 信息时间、是否存在有效首扫、等待自然日。

### 7.6 R04 运输超时/官方延误

**命中条件**：

1. 存在渠道 × 目的国家有效 SLA；
2. 当前时间超过 `签出时间 + 承诺妥投时效 + 2 个工作日`，或17TRACK子状态为 `Exception_Delayed`；
3. 仍未进入 OutForDelivery、Delivered、AvailableForPickup；
4. 轨迹仍有正常更新；
5. 同步状态为 success。

**排除条件**：已签收、退运、派送失败、同步失败、关键时间缺失。

**恢复条件**：恢复正常运输、进入派送、等待自提、已签收、退运，或规则配置变化后不再命中。

**展示证据**：签出时间、渠道 SLA、缓冲天数、已运输工作日、最新轨迹。

### 7.7 R05 物流断更

**命中条件**：已产生至少一条有效物流轨迹，最近一条有效轨迹距当前时间超过 3 个工作日，期间完全没有新的有效轨迹。

**排除条件**：17TRACK 主状态为 AvailableForPickup、DeliveryFailure、Delivered；已存在退运状态；同步状态为 failure 或 stopped；缺少最近有效轨迹时间。

**恢复条件**：产生新的有效轨迹，或进入等待自提、派送失败、退运、已签收。

**展示证据**：最近有效轨迹、断更工作日、同步时间、排除规则检查结果。

### 7.8 R06 物流停滞

**命中条件**：运输途中包裹在同一标准化地点停留超过 3 个工作日。

地点标准化优先使用国家/州/城市/邮编；无结构化地点时使用清洗后的地点文本。仅更新时间变化但地点和业务节点无实质变化，不视为离开该地点。

**排除条件**：海关节点、等待自提、派送失败、退运、已签收、同步失败。

**恢复条件**：产生不同地点的有效轨迹，或进入新的有效业务节点。

**展示证据**：首次到达该地点时间、当前地点、停滞工作日、期间轨迹列表。

### 7.9 R07 海关卡关

**命中条件**满足任一条件：

1. 最后有效节点被识别为海关、清关、查验或缴税相关节点，并持续超过 3 个工作日；
2. 17TRACK 返回 `InTransit_CustomsRequiringInformation` 或等价状态，明确表示清关需要补充资料。事件型卡关无需等待 3 个工作日。

识别依据优先顺序：17TRACK 标准子状态 > 运输商标准事件代码 > 多语言关键词规则。

**排除条件**：已明确放行、已离开海关地点、已退运、已签收、同步失败。

**恢复条件**：资料补充完成、出现清关放行或后续运输轨迹。

**展示证据**：到达海关时间、海关节点原文、标准化类别、停留工作日。

### 7.10 R08 派送异常

这是一个业务处理分组，但必须保留不同 17TRACK 原始状态：

1. DeliveryFailure：主状态为派送失败，子状态包括无人签收、安全原因、拒收、地址错误等。
2. AvailableForPickup：主状态为等待自提，业务上需要客服联系客户，但不得改写成派送失败。
3. Exception_Rejected：17TRACK若以异常主状态表达收件人拒收，业务上仍归入派送异常，但原始主/子状态保持不变。

**命中条件**：当前主状态为 DeliveryFailure 或 AvailableForPickup，子状态为 `DeliveryFailure_Rejected`/`Exception_Rejected`，或存在尚未被后续成功派送覆盖的相关事件。

**恢复条件**：产生重新派送、派送成功、签收或退运结果。

**展示证据**：原始主状态、子状态、失败/待自提时间、原因、最新轨迹。

### 7.11 R09 包裹退运

**命中条件**：17TRACK 主/子状态或标准事件显示包裹退回发件人、退运中或退运完成。优先使用标准子状态，例如 `Exception_Returning`。

**恢复条件**：退运属于终态型异常，默认不自动恢复；进入已签收且确认投递成功时可由规则或人工关闭。

**展示证据**：退运原因、首次退运时间、当前退运节点和轨迹。

### 7.12 R10 其他异常

其他异常是兜底分类，不是“所有17TRACK Exception状态”的集合。

**命中条件**：17TRACK异常无法归入运输异常、海关卡关、派送异常或包裹退运等明确规则。P0主要覆盖 `Exception_Lost`、`Exception_Damage`、`Exception_Destroyed`、`Exception_Security`、`Exception_Cancel`、`Exception_Other`。

**明确排除**：

1. `Exception_Delayed` → 运输异常；
2. `InTransit_CustomsRequiringInformation` 等清关补资料状态 → 海关卡关；
3. `DeliveryFailure_Rejected`、`Exception_Rejected` → 派送异常；
4. `Exception_Returning/Returned` → 包裹退运。

**恢复条件**：恢复正常运输、成功签收或人工确认关闭。

**展示证据**：17TRACK主状态、子状态、原始描述、首次发生时间、最新轨迹。列表显示“其他异常”，详情必须展示具体原因，例如丢失、破损或销毁。

### 7.13 多预警与去重示例

运单超过 SLA 且 4 个工作日无更新时，同时命中“运输超时”和“物流断更”。列表仅展示一行，主预警显示“物流断更”，次预警显示“运输超时”。进入新的运输节点后：

1. 物流断更恢复；
2. 若仍超过 SLA，则运输超时继续 active 并成为主预警；
3. 当前异常包裹总量仍按一个运单计算。

### 8.3 SLA 规则

唯一维度：物流渠道 + 17TRACK 运输商代码 + C端物流商 + 目的国家 + 生效日期区间。

字段包括：承诺妥投工作日、超时缓冲工作日、工作日历、优先级、生效时间、失效时间、启停状态。C端物流商为空时表示渠道默认规则；存在更精确规则时优先使用。

### 8.4 渠道和物流商字段边界

| 字段 | 含义 | 示例 |
|---|---|---|
| logistics_channel | 公司内部购买和结算的物流产品/渠道 | WYT-WF5日达 Zonal、云途英国专线 |
| carrier_code | 注册17TRACK时使用的运输商代码 | yunexpress、usps、ups |
| c_end_carrier | 消费者最后一公里实际看到的物流商 | GOFO、SpeedX、USPS、Royal Mail |

### 8.5 可选关联数据

P0 只预留字段，不强制接入：UCC 服务单号/状态/URL、TOS 解决方案、重发单号、退款金额、客服标签。

## 9. 数据导入与同步

### 9.1 Excel 导入校验

1. 按表头名称匹配，不依赖固定列顺序。
2. 运单号强制按文本读取。
3. `tracking_number + carrier_code` 去重。
4. 同一履约单允许多个不同追踪键。
5. 缺少签出时间的数据允许导入，但标记为数据不完整，不参与时间类预警。
6. 运单号为空、占位值“19”或运输商代码无法映射时拒绝进入轨迹监控。
7. 导入前展示原始行数、有效追踪键、重复行、拒绝行和警告行。
8. 提供问题数据下载，包含原行号、错误字段和处理建议。

### 9.2 17TRACK 同步策略

1. 新运单导入后进入注册/同步队列。
2. 活跃运输中的运单按接口额度配置同步频率，产品默认目标为 10 分钟。
3. 已签收运单完成最后一次同步后归档。
4. 同步失败采用指数退避重试，并记录失败原因。
5. 连续失败不得改写上一条成功轨迹，不得触发未上网或断更。
6. 每次成功同步后触发轨迹标准化、规则重算和生命周期更新。
7. 前端数据自动刷新目标为 5 分钟，支持手动刷新单个运单。

### 9.3 数据保留

1. 业务预警默认监控周期为 30 天；超过 30 天仍未解决时继续保留记录，并提示可手动归档，不强制删除17TRACK追踪数据。
2. 手动归档只结束当前业务预警监控，`alert_instance` 进入 archived；不得删除或改写17TRACK主状态、子状态、同步结果和完整轨迹。
3. Delivered 运单自动归档，不再进入当前预警，但继续参与渠道时效统计。
4. 物流未上网自动恢复后，不设置独立历史列表入口，只在履约单详情保留触发、恢复和持续时长痕迹。
5. 轨迹原始事件、规则命中历史和操作日志建议至少保留 2 年，最终以公司数据政策为准。

## 10. 信息架构

系统保留四个一级入口：

1. 数据总览。
2. 轨迹监控。
3. 渠道时效。
4. 数据与规则。

不设置独立的运单追踪、通知中心、工单、AI 或索赔导航。

#### 11.2.2 搜索与筛选

支持运单号、订单号、履约单号精准搜索，并支持以下组合筛选：

1. 日期：默认近 3 个月；快捷选项包括最近3天、昨天、近7天、近1个月、近3个月、自定义日期。

#### 11.2.6 详情抽屉/详情页

分成四个区块：

1. **履约基础信息**：支付时间、履约单创建时间、签出时间、签收时间、所属团队、发货仓、目的国家、物流渠道、C端物流商；履约单号可跳转ERP详情。
2. **物流事实**：17TRACK 主状态、子状态、运输商原始状态、最后同步时间。
3. **业务判断**：主预警、次预警、命中时间、持续时间、严重度、完整判断依据；物流未上网恢复记录只在此处保留。
4. **完整轨迹**：合并 ERP 履约单创建、签出节点和 17TRACK 轨迹，标记数据来源。
5. **协作信息**：处理标签、备注、UCC 服务单链接、重发/退款结果（有数据时展示）。

当同步失败时，详情顶部显示数据健康警告，并明确提示“当前暂停依赖轨迹的时间类预警判断”。

### 11.3 渠道时效

#### 11.3.1 筛选维度

团队、发货仓、目的仓、物流渠道、17TRACK运输商、C端物流商、国家、州、邮编、创建日期、签出日期、签收日期、自定义 N 天。

#### 11.3.2 核心指标

1. 平均妥投时效。
2. N 天达成率。
3. 渠道承诺时效达成率。
4. 超时率及超时 1-2、3-4、5-6、7 天以上分层。
5. 2-3、4-6、7-10、10 天以上无更新率。
6. 派送失败率。
7. 退运率。

#### 11.3.3 统计口径

**实际运输天数**：`delivered_at - shipped_at`。默认展示自然日，可切换工作日。

**平均妥投时效**：已妥投履约包裹实际运输天数总和 / 已妥投履约包裹数。

**N 天达成率**：签出日期队列中，在 N 天内已妥投的追踪键数 / 已具备完整 N 天观察窗口的有效追踪键数。未满观察窗口的包裹不进入分母，避免近期发货数据造成偏差。

**渠道承诺时效达成率**：在渠道 × 国家承诺工作日内妥投的追踪键数 / 已妥投有效追踪键数。

**超时率**：超过承诺妥投时效的已妥投追踪键数 / 已妥投有效追踪键数。

**无更新率**：运输期间曾出现对应连续无有效轨迹间隔的追踪键数 / 进入运输的有效追踪键数。同一追踪键在同一区间只计一次。

**派送失败率**：曾产生 DeliveryFailure 轨迹的追踪键数 / 有效追踪键总数。

**退运率**：曾产生退运轨迹的追踪键数 / 有效追踪键总数。

所有分母排除取消、测试、追踪键无效、关键时间缺失和数据同步不可用的记录，并支持查看被排除数量。

#### 11.3.4 图表和下钻

1. N 天达成率趋势。
2. 渠道对比柱状图。
3. 渠道 × 国家表现矩阵。
4. 轨迹稳定性分层图。
5. 派送失败/退运率对比。

点击渠道或国家后，下钻到对应运单明细，并保留筛选条件。

### 11.4 数据与规则

#### 11.4.1 数据源

展示 ERP/Excel 最近导入时间、17TRACK 最近同步时间、同步成功率、失败数、字段完整率和渠道映射异常。

#### 11.4.2 SLA 管理

支持新增、编辑、停用和查看渠道 × 国家 SLA。规则保存前校验日期重叠和同优先级冲突。

#### 11.4.3 预警规则

P0 允许管理员调整团队、发货仓、物流渠道、C端物流商、国家、阈值、工作日历、轨迹关键词、排除关键词、启停状态和优先级。关键词仅用于运输商原始文案的辅助判断；17TRACK标准主/子状态优先级高于关键词。规则的核心语义和排除条件采用受控配置，不允许任意脚本输入。

同一底层规则允许按“全局默认 → 团队/仓库 → 渠道/国家 → C端物流商”的顺序配置更精确覆盖。发布前必须检查范围重叠、优先级冲突和缺省规则。

#### 11.4.4 数据质量

展示运单号缺失、运输商无法映射、签出时间缺失、同步失败、轨迹时间异常、重复追踪键等问题，并支持导出问题数据。

## 12. 角色视图差异

### 12.1 物流部默认视图

默认进入“当前预警”，优先展示履约准备异常、未上网、运输异常、退运和其他异常；默认列包含团队、发货仓、渠道、C端物流商、国家、SLA、异常持续时间和最新轨迹。

### 12.2 客服部默认视图

默认筛选派送异常及带“需联客”标签的运单，覆盖派送失败、等待自提、地址错误和收件人拒收；默认列包含订单号、履约单号、失败原因、联系方式状态和 UCC 服务单。

### 12.3 共享行为

两个角色看到同一份物流事实和预警结果，仅默认筛选、可编辑字段和操作入口不同，不建设两套数据或两个重复模块。

## 13. 处理与审计

### 13.1 处理状态

每个 active 预警支持待跟进、已跟进、已解决。处理状态属于预警实例，而不是 17TRACK 状态。

### 13.2 备注

支持追加备注，不覆盖历史备注。记录操作者、时间、预警实例和内容。

### 13.3 自动恢复

物流恢复时，预警规则自动关闭 active 实例并写入恢复时间和恢复证据。人工“已解决”不强制关闭业务预警；如果物流仍命中，列表继续保留并显示“已处理但仍异常”。

### 13.4 手动归档

1. 只有业务预警实例可以手动归档，17TRACK官方状态和轨迹不可归档删除。
2. 用户从列表勾选运单后执行归档，系统必须二次确认并写入操作者、时间和原因。
3. 归档后退出“当前预警”，在“全部运单 → 已归档”中可查询。
4. 若归档后出现新的高风险17TRACK状态或满足重新监控条件，可生成新的预警实例，不复用旧实例。

### 13.5 操作日志

记录规则变更、手动标签、处理状态、备注、归档、导入、手动同步和导出行为。

## 14. 建议技术架构

### 14.1 处理链路

`履约数据导入/同步 → 追踪键标准化 → 17TRACK 注册与同步 → 轨迹事件标准化 → 预警规则计算 → 生命周期更新 → 查询与分析聚合`

### 14.2 后台任务

1. fulfillment_import_job：解析和校验履约数据。
2. tracking_register_job：向 17TRACK 注册新追踪键。
3. tracking_sync_job：拉取或接收最新轨迹。
4. event_normalize_job：标准化状态、地点和有效事件。
5. alert_evaluate_job：幂等计算十条底层规则并聚合为六个一级分类。
6. lifecycle_archive_job：恢复、30 天归档和签收归档。
7. metrics_aggregate_job：生成渠道和总览统计。

所有任务必须支持幂等、重试、失败记录和人工重跑。

## 17. 非功能需求

### 17.1 性能

1. 10 万监控运单规模下，列表查询 P95 ≤ 2 秒。
2. 单运单详情 P95 ≤ 1.5 秒。
3. 常用筛选条件必须走索引或聚合表。
4. 大规模导出采用异步任务，避免阻塞页面。

### 17.2 可用性

1. 同步或规则计算失败可重试且不丢失上一版有效结果。
2. 关键后台任务提供运行状态、失败数和最后成功时间。
3. 预警实例计算必须幂等。

### 17.3 安全

1. 采用公司统一登录和角色权限。
2. 页面默认隐藏客户敏感信息，本期无必要不展示姓名、电话和详细地址。
3. 导入、导出、规则修改和手动归档必须审计。
4. 17TRACK 密钥只存服务端密钥系统，不写入前端或日志。

### 17.4 可观测性

监控 17TRACK 请求量、成功率、限流、延迟、规则计算耗时、队列积压、异常数量突增和数据新鲜度。

## 18. 验收标准

### 18.1 状态与数据

- [ ] 17TRACK 九类主状态和子状态可原样展示。
- [ ] 业务预警不会覆盖 17TRACK 状态。
- [ ] 同步失败时不会新增未上网、断更、停滞或卡关预警。
- [ ] 运单号 + 运输商代码作为唯一追踪键。
- [ ] 同一履约单可关联多个运单。

### 18.2 预警规则

- [ ] 十条底层规则均可通过测试数据命中、持续和恢复，并正确聚合为六个一级分类。
- [ ] 履约单报错和超时未签出发生在17TRACK注册前，不错误关联官方状态。
- [ ] InfoReceived/电子面单创建不被视为有效上网。
- [ ] AvailableForPickup 不被归类为物流断更，也不被改写为 DeliveryFailure。
- [ ] 海关卡关独立于普通物流停滞。
- [ ] `Exception_Delayed` 归入运输异常。
- [ ] `InTransit_CustomsRequiringInformation` 归入海关卡关且无需等待3个工作日。
- [ ] `DeliveryFailure_Rejected` 和 `Exception_Rejected` 归入派送异常。
- [ ] 其他异常只承接未命中明确规则的17TRACK异常。
- [ ] 同一运单多预警只展示一行，并保留主预警和次预警。
- [ ] 恢复后自动退出当前预警，但历史记录仍可查询。
- [ ] 二次异常只作为业务标签，不进入六类当前预警统计。

### 18.3 页面

- [ ] 数据总览的卡片和图表可联动到轨迹监控。
- [ ] 可按运单号、订单号、履约单号精准搜索。
- [ ] 日期默认近3个月，并支持最近3天、昨天、近7天、近1个月、近3个月和自定义日期。
- [ ] LM、FD、LM_TT、网红团队切换后，全页统计和列表同步更新。
- [ ] 发货仓只显示万邑通仓和国内仓；C端物流渠道选项随仓库联动且切仓自动重置。
- [ ] 17TRACK主状态和子状态显示数量，子状态默认展开。
- [ ] 当前预警和全部运单模式结果正确。
- [ ] 详情能够查看物流事实、业务判断、完整轨迹和协作记录。
- [ ] 详情展示支付时间、履约单创建时间、签出时间、签收时间和C端物流商，履约单号可跳转ERP。
- [ ] 渠道时效支持自定义 N 天并能下钻明细。
- [ ] 物流部与客服使用同一数据，但默认视图和操作权限不同。

### 18.4 数据处理

- [ ] Excel 导入能够识别重复、缺失、占位和长运单号问题。
- [ ] 导入问题数据可下载并定位到原行。
- [ ] 17TRACK 同步失败可重试且有错误记录。
- [ ] 已签收和超过监控周期的运单按规则归档。
- [ ] 手动归档只影响业务预警，17TRACK状态与轨迹仍可查询。

### 18.5 指标

- [ ] N 天达成率只使用具备完整观察窗口的样本。
- [ ] 所有指标可查看分母、排除量和口径说明。
- [ ] 渠道 × 国家 SLA 变更不覆盖历史规则版本。

## 19. 测试场景清单

1. 发货 49 小时只有 InfoReceived：命中未上网。
2. 发货 30 小时产生 PickedUp：不命中未上网。
3. InTransit 连续 4 个工作日无有效轨迹：命中断更。
4. AvailableForPickup 连续 4 个工作日无更新：不命中断更，命中派送异常。
5. 海关节点停留 4 个工作日：命中海关卡关，不命中普通停滞主分类。
6. 同地点停留 4 个工作日但非海关：命中物流停滞。
7. 超 SLA 2 个工作日且轨迹持续更新：命中运输超时。
8. 同时超 SLA 且 4 个工作日无更新：主预警断更，次预警运输超时。
9. 同步连续失败：显示数据健康异常，不新增时间类预警。
10. DeliveryFailure_InvalidAddress：保留主/子状态并命中需客服跟进。
11. Exception_Returning：命中退运预警。
12. 预警恢复后产生新轨迹：active 关闭并变为 recovered。
13. 已重发的未上网包裹最终 Delivered：自动增加二次异常标签，不新增当前预警。
14. 同一运单号、不同 carrier_code：生成两个不同追踪键。
15. 已签收运单：自动归档并继续参与时效统计。
16. 履约单创建25小时仍未签出：命中超时未签出；回传签出时间后自动恢复。
17. ERP因邮编错误无法生成履约单：命中履约单报错；重试成功后进入正常履约流程。
18. Exception_Delayed：归入运输异常，不进入其他异常。
19. InTransit_CustomsRequiringInformation：立即归入海关卡关，无需等待3个工作日。
20. DeliveryFailure_Rejected 或 Exception_Rejected：归入派送异常。
21. Exception_Lost：未命中其他明确规则时归入其他异常，详情显示具体原因“丢失”。
22. 同一运单同时命中断更和运输超时：列表一行显示主预警和 +1，详情保留两条证据。
23. 手动归档 active 预警：退出当前预警，但17TRACK状态、子状态和历史轨迹仍可查询。
24. 选择万邑通仓后显示GOFO/SpeedX等C端渠道；切换国内仓后不再显示不适用选项。
