# 履约轨迹监控系统——业务需求与实现方案（Battle 版）

> 文档用途：业务方与产品经理、研发、数据团队对齐产品定位、需求范围、业务规则和验收标准  
> 核心用户：物流部、客服部  
> 产品主线：物流轨迹监控、业务预警、渠道分析  
> 当前 Demo：[履约雷达](https://fulfillment-control-tower.zengyun666.chatgpt.site/?v=18)

---

## 1. 先说结论

我们需要的不是一个“大而全”的履约中台，也不是新的客服工单系统，而是一个轻量的物流履约雷达：

1. 用 ERP 数据确认“业务上发生了什么”；
2. 用 17TRACK 数据确认“包裹实际上走到哪里”；
3. 用公司自己的规则判断“现在是否需要人工关注”；
4. 用渠道分析判断“哪个团队、渠道、国家经常出问题”。

产品的核心价值不是展示更多状态，而是让物流部和客服快速回答三个问题：

- 现在有哪些包裹需要处理？
- 为什么被判定为异常？
- 哪些渠道的时效和稳定性持续变差？

因此，一期只应围绕四个页面建设：

1. 数据总览；
2. 轨迹监控；
3. 渠道时效；
4. 数据与规则。

以下能力不应在一期扩张：独立工单中心、AI 异常识别、站内通知中心、索赔管理、客服模板平台、物流成本核算和完整订单履约链路。

## 2. 业务现状与痛点

### 2.1 当前问题

- 17TRACK 能告诉我们物流状态，但不能完全代表公司的业务风险；
- 同一主状态下可能存在完全不同的原因，需要查看子状态和轨迹；
- 物流人员大量依赖人工查看轨迹，发现异常较晚；
- 客服往往在客户投诉后才知道包裹派送失败或等待自提；
- 不同渠道、国家、团队的承诺时效不同，不能用同一个天数判断；
- 一个履约单可能同时命中多种预警，容易造成列表重复、统计重复；
- 包裹恢复正常后，如果直接删除预警，就无法追溯它曾经超时；
- ERP 报错、17TRACK 同步失败、真实物流异常容易混在一起，导致误报。

### 2.2 业务目标

- 从“客户投诉后处理”转成“系统主动发现”；
- 物流部每天优先处理高风险异常，而不是逐票查轨迹；
- 客服能够快速找到需要联系客户的派送异常；
- 管理者能够比较 LM、FD、LM_TT 三个团队及不同渠道的表现；
- 每一条预警都能解释命中依据、排除条件和恢复原因。

## 3. 产品边界

### 3.1 本系统负责什么

- 接收 ERP 履约单、订单、签出、渠道、团队等事实数据；
- 对接 17TRACK，保存官方主状态、子状态和完整轨迹；
- 根据业务规则产生、更新、恢复和归档预警；
- 提供团队、日期、渠道、国家、优先级等筛选；
- 展示渠道时效、稳定性和派送质量；
- 提供轻量标签、备注、服务单跳转等协作入口。

### 3.2 本系统不负责什么

- 不替代 ERP 创建或修改履约单；
- 不修改 17TRACK 的官方状态；
- 不替代 UCC 客服服务单；
- 不建设新的工单流转系统；
- 不承担客户消息发送平台；
- 不做索赔、审批、赔付和财务核算；
- 不做 AI 邮件、群消息解析；
- 不做库存、加工、仓储等全链路控制塔。

### 3.3 Battle 口径

如果一个功能不能直接提高“发现异常、定位原因、判断渠道表现”的效率，就不应该进入一期主流程。

## 4. 用户与使用方式

| 用户 | 最关注内容 | 默认视图 | 可执行操作 |
|---|---|---|---|
| 物流部 | 未上网、断更、停滞、海关卡关、运输超时、退运 | 全部物流预警，按优先级排序 | 查轨迹、写备注、标记处理、手动归档 |
| 客服部 | 派送失败、等待自提、地址错误、拒收 | 需要联系客户的预警 | 查履约单、打标签、跳转 UCC 服务单 |
| 管理员 | 数据质量、规则、SLA、权限 | 数据与规则 | 维护规则、渠道时效、字典和数据源 |

系统由物流部和客服部共用，但不应为两类用户各做一套重复页面。建议共用同一个轨迹监控页，通过“角色默认筛选 + 权限”提供不同视图。

## 5. 数据来源与事实所有权

### 5.1 ERP 是业务事实来源

ERP/导入表负责提供：

- 订单号；
- 履约单号；
- 运单号；
- 团队（LM、FD、LM_TT）；
- 发货仓、目的仓；
- 物流渠道；
- 目的国家、州、邮编；
- 支付时间；
- 履约单创建时间；
- 签出时间；
- 签收时间；
- C 端物流商；
- ERP 状态、错误码和错误描述。

### 5.2 17TRACK 是物流事实来源

17TRACK 负责提供：

- 运输商代码；
- 9 个官方主状态；
- 30 个官方子状态；
- 轨迹事件、时间、地点和运输商原文；
- 最后同步时间、同步结果和错误信息。

### 5.3 数据所有权原则

| 数据 | 唯一事实来源 | 业务规则是否可修改 |
|---|---|---:|
| 团队、履约单、订单、签出时间、渠道 | ERP | 否 |
| 主状态、子状态、轨迹 | 17TRACK | 否 |
| 业务预警、优先级、处理标签 | 本系统规则 | 是 |
| 渠道承诺时效 | 公司 SLA 配置 | 是 |

原则：来源系统事实只能读取和保存，不能被业务预警覆盖。

## 6. 17TRACK 状态与业务预警如何共存

### 6.1 三层信息必须同时存在

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| 17TRACK 主状态 | 包裹当前处于哪个物流阶段 | `InTransit` |
| 17TRACK 子状态 | 当前具体节点或原因是什么 | `InTransit_CustomsProcessing` |
| 业务预警 | 公司是否需要人工处理 | 海关卡关 |

它们不是三选一，同一运单应同时保存并展示。

例如：

```text
17TRACK 主状态：InTransit（运输途中）
17TRACK 子状态：InTransit_CustomsProcessing（海关处理中）
业务预警：海关卡关（超过 3 个工作日）
```

### 6.2 业务预警不能覆盖官方状态

错误做法：把 17TRACK 的 `AvailableForPickup` 改成“派送失败”。

正确做法：

- 官方主状态仍显示 `AvailableForPickup`；
- 官方子状态仍原样保存；
- 业务层将其归入“派送异常”，提醒客服主动联系客户自提。

### 6.3 点击预警后的状态联动

点击业务预警时，系统应自动带入相关的 17TRACK 状态筛选，但不能修改状态。

| 业务预警 | 自动关联的 17TRACK 状态 |
|---|---|
| 物流未上网 | `NotFound`、`InfoReceived`，并检查是否缺少有效首扫 |
| 运输超时 | `InTransit`、`Expired`，排除已派送和已签收 |
| 物流停滞 | 以 `InTransit` 为主，并进一步判断地点是否移动 |
| 海关卡关 | `InTransit_CustomsProcessing` 等海关相关子状态 |
| 物流断更 | 以 `InTransit` 为主，排除派送失败、等待自提和同步失败 |
| 派送异常 | `DeliveryFailure`、`AvailableForPickup` 及其子状态 |
| 包裹退运 | `Exception_Returning`、`Exception_Returned` 等 |
| 超时未签出 | ERP 履约状态，与 17TRACK 无直接状态映射 |
| 履约单报错 | ERP 错误码，与 17TRACK 无直接状态映射 |

联动的本质是“自动增加筛选条件”，不是把两个状态合并成一个状态。

## 7. 业务预警范围

最新范围应明确为 10 条底层预警规则：2 类 ERP 前置预警 + 8 类物流轨迹预警。页面可按更少的一级分类聚合展示，但规则仍需独立计算。

### 7.1 ERP 前置预警

| 预警 | 触发条件 | 恢复条件 | 主要处理人 |
|---|---|---|---|
| 超时未签出 | 履约单生成后 24 小时仍未完成签出 | ERP 回传签出时间 | 物流部/仓库 |
| 履约单报错 | ERP 因地址、城市、邮编或物流取号失败，无法生成履约单或运单号 | ERP 重试成功并生成履约单/运单号 | 业务/物流部 |

### 7.2 物流轨迹预警

| 预警 | 核心定义 | 主要排除条件 | 恢复条件 |
|---|---|---|---|
| 物流未上网 | 签出后超过 2 个自然日仍无承运商有效首扫 | 签出时间缺失、同步失败、运单无效 | 出现有效揽收/实体首扫 |
| 运输超时 | 超过渠道 × 国家承诺时效 2 个工作日，仍未进入派送，轨迹仍正常更新 | 派送失败、退运、断更、已签收 | 进入派送、待自提或签收 |
| 物流停滞 | 仍有新轨迹，但连续超过 3 个工作日停留在同一标准化地点 | 海关节点、等待自提、派送失败 | 地点或实际业务节点发生变化 |
| 海关卡关 | 海关相关节点持续超过 3 个工作日 | 已放行、离开海关、同步失败 | 出现放行或后续运输轨迹 |
| 物流断更 | 最后一条有效轨迹后超过 3 个工作日完全没有新有效轨迹 | 派送失败、等待自提、退运、已签收、同步失败 | 产生新有效轨迹 |
| 派送异常 | 17TRACK 显示派送失败或等待自提 | 已签收或已成功重新派送 | 重新派送、签收、退运或人工解决 |
| 包裹退运 | 17TRACK 识别为退运中或退运完成 | 无常规排除 | 默认终态，退运完成或人工关闭 |
| 渠道异常 | 17TRACK 识别为丢失、破损、销毁、延误、安全、取消或其他异常，且未归入更具体规则 | 已归入退运、派送异常或海关卡关 | 恢复运输、成功签收或人工确认关闭 |

### 7.3 渠道异常的分类边界

“渠道异常”是一级业务预警，主要承接17TRACK `Exception` 主状态中没有被现有业务规则覆盖的高风险子状态：

| 17TRACK子状态 | 渠道异常原因 | 建议基础优先级 |
|---|---|---|
| `Exception_Lost` | 丢失 | 紧急 |
| `Exception_Damage` | 破损 | 高 |
| `Exception_Destroyed` | 销毁 | 紧急 |
| `Exception_Delayed` | 延误 | 高；超过SLA时同时保留运输超时关联预警 |
| `Exception_Security` | 安全异常 | 高；若明确属于海关节点则优先归入海关卡关 |
| `Exception_Cancel` | 物流取消 | 高 |
| `Exception_Other` | 其他渠道异常 | 中，待人工确认 |

以下状态不进入渠道异常，避免重复：

- `Exception_Returning/Returned` → 包裹退运；
- `Exception_Rejected/NoBody` → 派送异常；
- 明确的清关状态 → 海关卡关；
- 已签收但时效超标 → 渠道时效分析，不进入当前预警。

## 8. 物流停滞与物流断更的区别

页面一级入口可以将两者合并为“运输异常”，减少预警卡片数量；但底层规则、异常子类型、命中证据和统计指标必须继续分开保存。这是最容易做重复的两条规则，必须互斥判断。

建议页面结构：

```text
运输异常 45
├── 物流停滞 27
└── 物流断更 18
```

点击“运输异常”展示两类履约单，并提供“全部 / 物流停滞 / 物流断更”二级筛选。履约单列表和详情仍应明确显示实际子类型，不能只显示模糊的“运输异常”。

| 对比项 | 物流停滞 | 物流断更 |
|---|---|---|
| 是否产生新轨迹 | 有 | 没有 |
| 地点是否变化 | 没有实质变化 | 无新轨迹，无法判断变化 |
| 典型情况 | 每天重复扫描同一个处理中心 | 最后一条轨迹之后完全无消息 |
| 恢复条件 | 新地点或新业务节点 | 任意新的有效轨迹 |

判断顺序：

```text
最近 3 个工作日完全无有效轨迹 → 物流断更
最近仍有轨迹，但地点/处理节点未移动 → 物流停滞
轨迹位于海关节点 → 优先判断海关卡关
```

“Label Created”“Electronic Data Received”等电子占位信息不能重置断更计时。

### 8.1 为什么只合并页面入口，不合并规则

- 两者命中依据不同：一个有新轨迹，一个没有新轨迹；
- 两者恢复条件不同：一个需要地点变化，一个只需要出现新有效轨迹；
- 渠道质量指标不同：停滞率和断更率需要分别分析；
- 如果规则也合并，后续无法解释为什么系统报错，也无法准确衡量渠道问题。

## 8A. 运输超时如何区分未妥投和已妥投

运输超时应分成“需要处理”和“用于分析”两个结果，不能全部堆进当前预警。

| 情况 | 产品处理 | 原因 |
|---|---|---|
| 未妥投且超过 SLA + 缓冲期 | 进入当前预警，显示为运输超时 | 包裹仍在途，物流部还有机会介入 |
| 已进入派送/等待自提 | 退出普通运输超时，按派送状态处理 | 当前动作已由末端状态决定 |
| 已妥投但实际时效超过 SLA | 不进入当前预警；计入妥投超时率和渠道分析 | 包裹已完成，无需再占用处理队列 |

未妥投超时的规则建议：

```text
当前未妥投
AND 当前时间 > 签出时间 + 渠道承诺时效 + 缓冲期
AND 尚未进入派送/待自提
AND 轨迹仍正常更新
→ 当前预警：运输超时
```

已妥投超时的处理建议：

- 签收后自动关闭当前运输超时预警；
- 在履约单详情保留运输超时的触发和签收恢复记录；
- 记录实际妥投天数、超 SLA 天数；
- 进入渠道时效页的“已妥投超时率”和超时天数分布；
- 不再占用物流部当前待处理数量。

## 9. 轨迹关键字怎么使用

需要支持关键字，但关键字只能作为辅助，不能成为所有规则的唯一依据。

### 9.1 判断优先顺序

1. 17TRACK 标准主状态和子状态；
2. 运输商结构化事件或地点；
3. 多语言轨迹关键字；
4. 时间阈值和排除条件。

### 9.2 规则配置需要支持

- 不使用关键字；
- 关键字辅助匹配；
- 必须命中关键字；
- 忽略关键字；
- 匹配轨迹标题、详情或 ERP 报错信息；
- 关键词组“任一命中”或“全部命中”。

### 9.3 为什么不能只靠关键字

- 不同运输商使用不同语言和文案；
- 同一关键词可能出现在正常和异常轨迹中；
- 运输商会修改文案，规则容易突然失效；
- 17TRACK 已经提供结构化状态时，优先使用结构化数据更稳定。

## 10. 同一履约单命中多个预警怎么处理

### 10.1 简单方案

- 同一履约单/运单在列表中只显示一行；
- 系统保存全部当前命中预警；
- 列表突出最高优先级的“主预警”；
- 其他预警显示为 `+N`；
- 点击详情查看全部主预警、关联预警和各自命中依据。

### 10.2 建议优先级

```text
履约单报错
> 超时未签出
> 包裹退运
> 派送异常
> 海关卡关
> 物流断更
> 物流停滞
> 物流未上网
> 运输超时
```

优先级可配置，但不能删除其他实际命中记录。

### 10.3 统计口径

- “当前异常履约单数”：按履约单/追踪键去重；
- “各预警类型数量”：分别统计命中，因此相加可能大于异常履约单总数；
- 页面必须明确口径，不能把两种数字混用。

### 10.4 状态变化示例

某包裹同时命中“物流断更”和“运输超时”：

1. 列表只显示一行，主预警为物流断更；
2. 出现新轨迹后，物流断更自动恢复；
3. 如果仍超过 SLA，运输超时继续存在并自动成为主预警；
4. 详情保留物流断更曾经发生和恢复的痕迹。

## 11. 恢复与归档策略

### 11.1 物流未上网的特殊处理

物流未上网即使后续自动恢复，也说明承运商首扫曾经超时，因此：

- 恢复后退出当前预警列表；
- 不额外建设复杂的历史预警中心；
- 仅在履约单详情中保留一条历史记录；
- 记录触发时间、恢复时间、超时时长和恢复原因。

### 11.2 归档什么

归档的是“业务监控展示和预警实例”，不是删除 17TRACK 官方状态和轨迹。

| 数据 | 归档后的处理 |
|---|---|
| 当前业务预警 | 从当前预警列表移出 |
| 预警命中和恢复历史 | 保留在履约单详情 |
| 17TRACK 主状态、子状态、轨迹 | 原样保留 |
| ERP 履约事实 | 原样保留 |
| 标签和备注 | 保留 |

### 11.3 自动归档

- 已签收订单自动归档；
- 超过默认监控周期 30 天仍未解决的记录进入归档视图；
- 预警恢复后退出当前预警，但无需把整张履约单立即删除。

### 11.4 手动归档

- 手动归档只关闭当前业务预警的展示；
- 必须记录操作人、时间和原因；
- 后续出现新的高优先级异常时，允许重新进入当前预警；
- 手动归档不能改写或删除 17TRACK 状态。

用于看全局结构，不承担逐票处理。

点击图表后跳转轨迹监控，并自动带入筛选条件。

### 12.2 轨迹监控

预警监控与运单追踪合并，不拆成两个重复模块。

#### 快捷切换

- 全部团队；
- LM；
- FD；
- LM_TT。

切换团队后，顶部数量、状态数量、预警数量和列表必须同时更新。

#### 日期筛选

- 最近 3 天；
- 昨天；
- 近 7 天；
- 近 1 个月；
- 近 3 个月；
- 自定义日期。

每次打开默认选择“近 3 个月”。日期口径默认使用签出日期，并允许切换创建日期、签收日期和异常创建日期。

#### 其他筛选

- 运单号、订单号、履约单号精准搜索；
- 物流渠道；
- 国家；
- 17TRACK 主状态和子状态；
- 业务预警类型；
- 优先级；
- 处理标签；
- 同步状态；
- 当前预警/全部运单/已归档。

#### 列表要求

- 点击预警卡片必须立即展示对应履约单，不能出现“卡片有数量、列表为空”；
- 17TRACK 主状态显示数量；
- 选择主状态后，子状态默认展开并显示各自数量；
- 运单号为可点击链接；
- 当前主预警、`+N`、优先级、17TRACK 状态和最新轨迹在同一行可识别；
- 点击一行打开履约单详情。

#### 履约单详情

1. ERP 事实：订单、履约单、支付时间、履约单创建时间、签出时间、团队、渠道、C 端物流商；
2. 17TRACK 事实：主状态、子状态、原始轨迹、同步时间；
3. 业务判断：主预警、关联预警、命中依据、持续时间；
4. 签收信息：已签收显示签收时间，未签收明确显示“未签收”；
5. 历史痕迹：已自动恢复的未上网、已妥投运输超时等历史预警；
6. 履约单号：显示为链接，点击后使用 ERP 详情 URL 模板打开对应履约单；
7. 协作信息：标签、备注、服务单跳转；
8. 手动归档入口。

ERP 跳转地址不要写死在页面代码中，应由管理员配置 URL 模板，例如：

```text
https://erp.company.com/fulfillment/{fulfillment_no}
```

系统只替换 `{fulfillment_no}` 并在新窗口打开；没有履约单号的 ERP 建单报错不能生成跳转链接。

### 12.3 渠道时效

这是分析页，不用于逐票处理。

需要支持按以下维度分析：团队、发货仓、目的仓、物流渠道、运输商、国家、州、邮编、创建日期、签出日期、签收日期。

核心指标：

- 平均妥投时效；
- 自定义 N 天达成率；
- 渠道承诺时效达成率；
- 超时率及 1–2、3–4、5–6、7 天以上分层；
- 2–3、4–6、7–10、10 天以上无更新率；
- 派送失败率；
- 退运率。

关键要求：渠道时效必须按“渠道 × 国家 × 生效日期”配置，不能全渠道使用一个 SLA。

### 12.4 数据与规则

将低频管理能力集中在此页面，避免轨迹监控页过于臃肿：

- 业务预警规则；
- 渠道 SLA 规则；
- 17TRACK 9 个主状态和 30 个子状态字典；
- 导入数据质量和字段映射；
- 工作日历、渠道映射和同步健康。

## 13. 业务规则配置应该包含什么

每一条规则至少需要以下配置项：

| 配置项 | 说明 |
|---|---|
| 规则名称和代码 | 保证规则可追溯 |
| 是否启用 | 支持暂停，不删除历史 |
| 适用团队 | 全部、LM、FD、LM_TT |
| 适用渠道/运输商 | 可指定或全部 |
| 适用国家 | 可指定或全部 |
| 数据来源 | ERP、17TRACK 或两者组合 |
| 关联主状态/子状态 | 只读映射或筛选条件 |
| 起算时间 | 履约创建、签出、最后有效轨迹、到达某节点 |
| 时间阈值 | 数值 + 自然日/工作日 |
| 轨迹关键字 | 可选辅助、必须命中或不使用 |
| 忽略关键字 | 排除占位或正常文案 |
| 排除条件 | 已签收、同步失败、等待自提等 |
| 恢复条件 | 自动退出预警的明确条件 |
| 优先级 | 紧急、高、中 |
| 生效区间 | 避免历史数据被新规则错误重算 |
| 版本号 | 保留当时采用的规则版本 |

产品经理不能只给一个“阈值输入框”。没有适用范围、排除条件、恢复条件和规则版本，后续一定会出现大量误报和不可追溯问题。

## 14. 实现方式

### 14.1 数据处理流程

```text
ERP/Excel 导入
    ↓
字段校验、运单号文本化、渠道与运输商映射
    ↓
注册并同步 17TRACK
    ↓
保存主状态、子状态和原始轨迹
    ↓
标准化有效轨迹、地点、海关节点和时间
    ↓
根据团队、渠道、国家、SLA 和业务规则计算预警
    ↓
确定主预警与关联预警
    ↓
展示列表、详情、趋势和渠道分析
    ↓
新轨迹到达后重新计算，自动恢复或重新激活
```

### 14.2 建议的数据分层

#### A. 履约单/运单事实表

保存 ERP 标识、团队、渠道、仓库、国家、签出时间及当前 17TRACK 状态。

追踪唯一键建议使用：

```text
标准化运单号 + 17TRACK 运输商代码
```

原因：相同运单号在不同运输商下不能直接视为同一包裹。

#### B. 轨迹事件表

每一条轨迹独立保存时间、地点、主状态、子状态、运输商原文、是否有效和来源。

#### C. 预警实例表

一条履约单/运单可以对应多条预警实例。每条实例保存：

- 预警类型；
- 规则版本；
- 命中时间；
- 当前状态；
- 持续时间；
- 命中证据；
- 恢复时间和恢复原因；
- 是否主预警；
- 归档信息。

#### D. 业务协作信息

标签、备注、负责人、UCC 服务单链接独立保存，不能塞进 17TRACK 状态字段。

### 14.3 规则计算机制

- 新履约数据导入后计算 ERP 前置预警；
- 每次 17TRACK 成功同步后重新计算轨迹预警；
- 同步失败时保留上次成功状态，并暂停依赖轨迹的时间类预警；
- 规则未恢复前只更新持续时间，不重复创建同类预警；
- 规则恢复后记录恢复原因，并退出当前预警；
- 规则变更要生成新版本，历史记录保留旧版本。

### 14.4 列表筛选实现原则

所有卡片、状态数量、子状态数量和明细列表必须读取同一套筛选条件和统计口径。不能分别写死数字，否则必然出现“上面显示 20 单，下面查不到数据”。

建议统一筛选对象：

```text
日期口径 + 日期范围 + 团队 + 渠道 + 国家
+ 17TRACK 主/子状态 + 业务预警 + 优先级
+ 生命周期 + 标签 + 同步状态 + 关键词搜索
```

### 14.5 更新频率

- 页面无需假装秒级实时；
- 目标可定义为轨迹入库后 5–10 分钟内完成预警更新；
- 支持单票手动刷新；
- 已签收包裹降低或停止同步频率；
- 17TRACK 接口限额、重试和失败退避由后端统一控制。

## 17. 验收标准

### 17.1 状态与预警

- 17TRACK 主状态和子状态原样保存，不被业务预警改写；
- 10 条预警规则均有明确触发、排除和恢复条件；
- 渠道异常覆盖丢失、破损、销毁、延误等17TRACK异常状态；
- 同一履约单多预警只展示一行，但详情能查看全部命中；
- 主预警自动随当前命中和优先级变化；
- 同步失败不能误报未上网、断更、停滞和海关卡关。

### 17.2 筛选与数量

- 默认日期为近 3 个月；
- 团队切换后所有数量和明细同步变化；
- 点击任何预警卡片，下方必须展示对应履约单；
- 选择 17TRACK 主状态后，子状态默认展开并显示数量；
- 支持优先级、渠道、国家和精准编号搜索；
- 卡片总数和列表数据使用同一查询口径。

### 17.3 恢复与归档

- 未上网恢复后退出当前预警；
- 未上网历史只在履约单详情留痕；
- 手动归档不删除 ERP 和 17TRACK 事实；
- 新的高优先级异常可使已手动归档的履约单重新进入当前预警；
- 已签收订单自动归档并可查询。

### 17.4 渠道分析

- 时效按渠道 × 国家规则计算；
- 当前运输超时只统计未妥投订单；
- 已妥投超时退出当前预警，但计入渠道妥投超时率和详情历史；
- N 天达成率排除观察窗口不足的新近发货包裹；
- 平均时效、SLA 达成率、断更率、派送失败率和退运率口径明确；
- 支持按团队、仓、渠道、国家和日期下钻。

## 18. 与产品经理 Battle 时需要坚持的点

### 18.1 “17TRACK 已有状态，为什么还要业务预警？”

因为 17TRACK 描述的是物流事实，业务预警判断的是公司是否需要介入。`InTransit` 本身不等于正常，同一个 `InTransit` 可能是正常运输、运输超时、停滞、断更或海关卡关。

### 18.2 “能不能把业务预警直接做成新的物流状态？”

不能。一个运单可能同时命中多个预警，且官方状态会继续变化。强行合并会丢失事实、产生互相覆盖，并导致后续无法解释。

### 18.3 “为什么要同时保存主预警和关联预警？”

只保留一个会丢失风险，只展示多行会导致重复处理和重复统计。主预警 + `+N` 是最轻量、最清楚的折中。

### 18.4 “恢复后直接删除不行吗？”

不行。曾经未上网或断更本身就是渠道质量问题。当前列表可以移除，但详情必须留痕，否则渠道分析和责任追溯失真。

### 18.5 “为什么停滞和断更不能合并？”

处理原因不同：停滞说明承运商持续扫描但包裹没移动；断更说明完全没有新有效轨迹。两者取证、责任判断和恢复条件都不同，但规则应互斥避免重复。

### 18.6 “为什么规则配置不能只填天数？”

因为相同天数在不同团队、渠道、国家、状态和工作日历下含义不同。没有适用范围、排除条件和恢复条件，只会产生大量误报。

### 18.7 “为什么一期不做工单、通知中心、AI 和索赔？”

这些属于其他系统已经覆盖或可以通过链接、摘要推送解决的能力。先把轨迹数据和预警准确率做好，才能决定后续是否需要更重的处理流程；否则只是把错误预警自动变成更多错误工单。

### 18.8 “Demo 已经有页面，是否代表可以直接上线？”

不代表。Demo 证明的是页面结构和业务交互，生产上线还必须完成真实数据接入、规则引擎、状态生命周期、权限、审计、性能和准确率验证。

### 18.9 “停滞和断更是不是可以直接合成一条规则？”

页面入口可以合并成“运输异常”，但规则不能合并。合并入口是为了减少页面复杂度；保留子类型是为了保证判断可解释、恢复准确、渠道指标可分析。

### 18.10 “已妥投但超时，为什么不继续显示当前预警？”

因为当前预警服务于“还有机会处理的订单”。已经妥投的订单没有现场处理动作，继续占用预警队列只会淹没真正未妥投的包裹；但它仍然必须进入渠道超时率、超时分布和履约单历史，不能丢失。

## 19. 产品评审必须当场确认的问题

1. 履约单、运单、订单三者的唯一标识和一对多关系是什么？
2. ERP 实际能够稳定提供哪些时间字段和错误码？
3. 签出时间是否确认是未上网和运输时效的统一起点？
4. 不同渠道 × 国家的 SLA 由谁维护，历史生效日期如何处理？
5. 工作日按目的国、发货国还是公司统一日历计算？
6. 派送异常由客服还是物流部主责，等待自提是否设独立处理时限？
7. 手动归档后，哪些新异常可以重新激活？
8. 17TRACK 允许的同步频率和账号额度是多少？
9. UCC/TOS 能提供哪些只读链接或回传字段？
10. P0 的预警准确率、更新延迟和使用覆盖率目标是多少？

这些问题没有确认前，可以做页面原型，但不能宣称业务规则已经具备可开发口径。

## 20. 最终业务口径

```text
ERP 和 17TRACK 提供事实；
业务规则只做判断，不改写事实；
同一履约单可以有多个预警，但列表只出现一次；
恢复后退出当前预警，必要痕迹保留在履约单详情；
归档业务预警，不删除 17TRACK 状态与轨迹；
物流轨迹监控是主线，客服协同和数据分析是辅助；
一期先保证预警准确、可解释、可恢复，不建设重型流程平台。
```
